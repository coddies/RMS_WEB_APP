# BUSINESS.md — Protection & Licensing Strategy

Managed entirely from the **Super-Admin Panel** (Feature 09) — restaurants never see or touch this layer.

---

## 1. License Protection (core request)

**Goal:** Software should only run for the restaurant it was installed for. Unauthorized copy to another machine/restaurant should refuse to run and show a contact message.

### How it works
1. Each tenant gets a one-time `rms_...` Pairing Key at onboarding. Store only its SHA-256 verifier in `tenants.license_key`; show the raw key once to the administrator.
2. On install, local-bridge hashes the Windows MachineGuid and registers it against the tenant's Pairing Key through the restricted `rms_pair_local_bridge` RPC. The RPC returns the tenant slug; the installer does not ask the restaurant to type it.
3. On every startup, local-bridge checks: does this machine's fingerprint match the registered one for this license key?
   - **Match:** runs normally.
   - **No match** (copied to another PC): refuses to start, shows:
     *"Unauthorized installation detected. For licensing support, contact: [your name/number]."*

### ⚠️ Critical constraint — do not break offline-first
Our core value prop is "works without internet." A license check that *requires* internet every time it starts would contradict that. Solution:
- Local-bridge caches a **signed license token** locally after a successful check.
- It works offline using that cached token for up to **N days (suggest 7)**.
- Only needs to "phone home" (re-verify with Supabase) once within that window.
- If it can't reach Supabase after the grace period expires, it shows a warning (not an immediate hard lock) and keeps a short additional buffer (e.g. 3 more days) before restricting new orders — never lose data, never block printing of already-placed orders.

### Kill-switch (tied to subscription)
- If `subscription_status` is set to `expired`/`suspended` in Super-Admin, the next phone-home check disables the local-bridge (same "contact for licensing" message, different reason text: "Subscription expired").
- This lets you remotely cut off a restaurant that stops paying, without visiting in person.

### Super-Admin visibility
Add to the Super-Admin restaurant detail view:
- License status (Active / Unregistered / Mismatched machine / Expired)
- Last phone-home timestamp
- Button: Revoke / Reissue license key (e.g. if restaurant gets a new PC)

## 2. Other Protection Measures Worth Adding

### 2.1 Excel Export Watermarking
Every auto/manual Excel export (Feature 08) gets a small footer: restaurant name + "Generated by [Your Platform Name]" + export timestamp. Doesn't block anything, but makes leaked/shared files traceable back to source and subtly reinforces branding.

### 2.2 Menu/Branding Anti-Scraping
Public menu pages are, by nature, visible to anyone (that's the point — customers need to see them). But a competitor could script-scrape a restaurant's full menu+prices repeatedly. Add a simple rate-limit (similar to the delivery-form rate limit already built) on the menu API per IP, to slow down bulk scraping without affecting real customers.

### 2.3 Source Code Protection (for the local-bridge .exe)
Since local-bridge code runs physically on a machine you don't control, it's more copyable than server code. Minimum protection: bundle/obfuscate the JS before packaging into the installer (not full reverse-engineering-proof, but raises the effort bar beyond a casual copy).

### 2.4 Audit Log
Log every license check (pass/fail/mismatch) to a `license_events` table — gives you a record if a restaurant disputes "we never copied it" or if you need to investigate suspicious activity.

## 3. Data Model Addition (ties into DB_SCHEMA.md)

```sql
alter table tenants add column license_key varchar unique; -- SHA-256 verifier; raw pairing key is never stored
alter table tenants add column hardware_fingerprint text;
alter table tenants add column license_status varchar default 'unregistered'; -- 'active' | 'mismatched' | 'expired' | 'unregistered'
alter table tenants add column last_check_in timestamptz;

create table license_events (
  id uuid primary key default gen_random_uuid(),
  tenant_id uuid references tenants(id),
  event_type varchar, -- 'check_in' | 'mismatch' | 'revoked' | 'reissued'
  details text,
  created_at timestamptz default now()
);
```

## 4. Where This Fits in Build Order
This is **not v1-launch-blocking** — ship the core product first, add licensing once you're onboarding real paying restaurants and the "someone could just copy my installer" risk becomes real (i.e. after a few restaurants are live, before scaling to many). See `features/11-license-protection.md` for the implementation spec when you're ready to build it.
